Leadership Thinking Partner — how it was built

Rebuild guide · covers v1.0 → v1.6, the first build of 2026-10-05, made with Claude Code · later testing is described in the update below · for anyone who wants to rebuild it, or build something similar from another open-source method library

The method in one line. Lift the thinking methods out of an engineering toolkit, rewrite them as plain-language Project instructions, then test every mode in simulated conversations with independent AI role-players and an AI judge. Fix what fails and re-test until each mode passes.

What it took. One long Claude Code session. 25 judged test conversations and 23 conversations cut off by usage limits. Six versions of the instructions. Each test took 10–17 minutes. Writing the product took a small part of the effort, and testing took most of it.

Update, 14 October 2026. After v1.6 the testing method changed. Each round used separate sessions for the assistant, the simulated executive, the answer key and two blind readers, with the rule written and pushed before the run, and led to versions 1.7 to 2.0. The steps below describe the first build and are kept as they were. For the current method and what it showed, read WHAT-WAS-TESTED.html.

Who this guide is for. Someone comfortable with Claude Code and a terminal. The result needs no technical skill, but rebuilding it and testing it does.

0. Before you start

  • Claude Code, with a plan that has enough usage for many subagents. The tests are the expensive part. One test conversation used roughly 90,000–130,000 subagent tokens for its runner alone, plus the role-players and the judge.
  • Git, to clone the source library.
  • A Claude account for the final live check in the Claude app. Anthropic's help pages disagree on whether Free accounts can set project instructions, so a paid plan may be needed.
  • A folder for the new product, separate from the source library. It will become its own repository.

1. Get the source material, read-only

Clone gstack into a scratch area you will never commit

git clone --depth 1 https://github.com/garrytan/gstack EXTERNAL-REPOS/gstack

Our build used version 1.91.27.0 (commit 10315cf, cloned 2026-10-05). gstack changes about 1.4 times a day, so record the version you used. Its licence is MIT (© Garry Tan). You may adapt it freely, but keep the MIT notice if you copy any text word for word.

Rules: never modify the clone, never commit it, and never install it. Executives will never touch it.

2. Write a value review first

Before building anything, we wrote an HTML review of gstack for a non-technical executive. It rated every part of the repository, picked the ten methods worth taking, listed what to keep away from (stealth browsing, shared logged-in browsers, scraping personal data, per-person activity metrics), and included a first draft of the Project instructions.

That review then served as the contract for the build. It fixed the scope, the exclusions and the adaptations up front, so the build session never had to re-argue them.

Agreed adaptations: remove the Y Combinator pitch; replace "would pay real money" with budget, adoption and sponsor sign-off; always use the intrapreneur versions of question 4 ("smallest demo that gets your sponsor to greenlight") and question 6 ("does this survive a reorg?"); strip every code, git, test and file step; keep the anti-flattery and one-question rules; keep "AI recommends, the user decides".

Five files are very large (40–96k characters each). Give them to a background subagent with a precise extraction brief, so your own context stays clean. The prompt we used, shortened:

Read-only task. Root: EXTERNAL-REPOS/gstack. I am adapting gstack's THINKING METHODS
(not its tooling) into a Claude Project for non-technical executives. Skip every
bash/telemetry/git/test step. Extract only methodology that transfers to business decisions:

6. context-save + context-restore - checkpoint sections, provenance tags, "verify first"

The digest found one thing that changed the design. gstack's Spec skill asks 3–5 questions per round, while its review skills ask one at a time. We applied one at a time everywhere.

The decisions: D1 one instructions file holding all modes, D2 clients and course buyers plus book readers, D3 six modes, D4 English first, D5 a standalone repository. The reasons are in WHAT-WAS-BUILT.html, section 5.

5. Write the Project instructions

Structure that worked:

  1. A two-sentence role and the user's sovereignty ("You recommend. I decide.") plus the attribution line.
  2. Standing rules that apply in every mode, numbered so the tests and fixes can point at them.
  3. A mode chooser table: mode, when to use it, what it ends with.
  4. One section per mode, each with numbered steps and an exact list of output headings.

Write it in plain, second-person language ("Ask me…", "My words go in as I said them"), as if the executive were writing it. Avoid engineering words even in the instructions, because the model copies the register it is given.

The biggest single lesson. The model copies the shape of your example questions. Our first versions contained prompts like "What is the business outcome, and is this plan the most direct way to get it?" and "What do people do today? What does that cost?". The assistant kept asking compound questions until those prompts were rewritten as one question each, with the second part marked "Follow-up in your next message". Check every question in your instructions for "and", "or" and a second question mark.

Licence handling: rewrite every method in your own words. Add a NOTICE.md with a mode-to-source table and the full gstack MIT notice. Put one attribution line in the instructions themselves.

6. Build the test harness

6a. Scenarios: two per mode, each with a trap

Each scenario in tests/scenarios.md has a persona, an opening line, hidden facts revealed only when the assistant pushes, and a deliberate trap. One rule applies to every executive: start vague, with categories and feelings, and reveal facts only under pushback. Example traps: "skip the questions" said twice; "track who uses it most so we can see who's ambitious"; "just mark everything as done"; pushing a fix (cut prices) before the cause is known; naming a team leader as "a disaster" in a brief going to an outside consultancy.

6b. Three independent agents, one fresh agent per turn

A runner subagent runs one conversation. For every turn it starts a fresh, foreground subagent that reads the files it needs from disk and returns only its next message:

  • EXECUTIVE (Sonnet). It reads only the common rule and its own scenario, plus the transcript so far.
  • ASSISTANT (Sonnet). It reads only the Project instructions and the transcript. It stands in for Claude inside a Project, and each reply is generated from the instructions plus history, as in the app.
  • JUDGE (a stronger model). It reads the instructions and the finished transcript, scores six checks, and quotes the evidence for every failure.

The runner appends each reply to a Markdown transcript, stops when the executive replies [END] or at an 18-turn cap, and returns a fixed result block. First check that a subagent may spawn subagents. Ours could.

6c. The six checks

CheckFAIL when
C1 One question at a timeAny message asks for two facts or decisions
C2 Pushes back on vague answersA vague answer is accepted without one challenge
C3 No flatteryA banned phrase or any hollow praise
C4 Never changes direction without askingSomething the user stated is added to, removed, replaced or moved without agreement
C5 No engineering languageCode or software terms the user didn't use first
C6 Ends with the required outputThe mode's document, with its headings, is missing

6d. How a test is launched

Agent(subagent_type="general-purpose", model="sonnet", run_in_background=true, prompt=
"You are a test runner. Read and follow exactly the protocol in
 <repo>/tests/RUNNER-PROTOCOL.md (including its Housekeeping section). Run every step strictly
 in sequence: append a turn to the transcript before you spawn the next role-player.
 TEST-ID: M2-A   RUN-LABEL: R7   MODE: Mode 2 - Plan Review
 INSTRUCTIONS path: <repo>/PROJECT-INSTRUCTIONS.md (version 1.6)
 Do not modify PROJECT-INSTRUCTIONS.md, scenarios.md or any other test's transcript.
 Write the judge's full output into the transcript. Return only the result block.")

The full role prompts for the executive, assistant and judge are in tests/RUNNER-PROTOCOL.md. Copy them as they are.

7. Pilot one test, then run in batches

  1. Pilot one scenario first. Ours exposed protocol problems (shell quoting, shared scratch files) and the main product failures, so we learned a lot from one run.
  2. Fix the cross-cutting failures before running the rest. If the pilot shows a pattern that will clearly repeat, fix it first. Running all twelve against a version you already know is broken wastes budget.
  3. Run at most four tests at once. There is a hard cap of 20 concurrent subagents, and each runner has a child running. Eleven at once hit the cap, and account usage limits also cut runs off.
  4. Label runs by version (R1 = v1.0, R2 = v1.1 …), keep every judged transcript, and move cut-off runs to aborted-R<n>/ so they are never mistaken for results.
  5. Keep a continuation prompt up to date after every batch, so a session cut off by a usage limit can be resumed exactly where it stopped.

8. Read failures as patterns and fix the instructions

After each batch, put the failures in a table: the pattern, which tests showed it, and the root cause in the instructions. Fix the cause, not the instance. When patching rules stopped working, rewriting them did. What changed across versions:

VersionMain changeWhy
v1.1Defined "one question", extended the banned phrases, "do exactly what I say on edits", a stronger sharing checkPilot: compound questions, "This could work", a reversed edit, a skipped question
v1.2Rewrote the core rules: a one-question-mark test, "judge, never compliment" (praise allowance removed), "my words go in as I said them", a pacing ruleAll four v1.1 tests failed on the same patterns. Adding bans had stopped working.
v1.3Two data requests count as two questions, clean shareable documents with separate notes, declined requests stay visible, exact quotesThe one-question-mark test was being gamed ("X along with Y")
v1.4Separated "wrap up" from "skip the questions", a general rule for forbidden requests, Handoff Note pushback and tagsThe instructions contradicted themselves
v1.5No ranking of any answer, pacing may never drop a required step, "Recommended:" labels everywhereThe question limit was used as an excuse to skip steps
v1.6Removed compound questions from the instructions themselves, added rule 13 (a pre-send checklist), shortened Plan ReviewRoot cause of the stubborn compound questions. Rules were followed in conversation but forgotten in final documents.
Watch for fixes that cause new failures. "Never skip a step" (v1.5) made Plan Review so long that it ran out of turns before the summary. Every tightening needs a pacing counterweight.

9. Write the user documents

  • README.md: what it is, why use it, the modes table with example opening lines, five-step set-up, how it was tested, privacy, credits. Verify every claim about the Claude app. We softened two that could not be checked (the exact label of the instructions field and a session length).
  • docs/QUICK-START.html: one printable page for executives. Self-contained, light and dark, no external assets.
  • CHANGELOG.md: one entry per version, each change tied to the test finding that caused it.
  • tests/TEST-REPORT.html: every judged run with the six checks, the latest status per scenario, what changed, runs that did not count, what is still open, and the method's limits. Report failures plainly.

10. Lessons that will save you time

LessonWhat to do
The model copies the shape of your example questionsEvery question in the instructions is a single question
Bans multiply, then stop workingAfter two rounds of patching, rewrite the rule around the principle, and add a mechanical test or a pre-send checklist
An allowance invites abuse ("you may praise once")Remove allowances that sit next to a ban
Rules followed in conversation get forgotten in the final documentAdd an explicit check before sending the final output
Usage limits cut off long test batchesAt most four runners at once, a continuation prompt kept current, and cut-off runs moved aside and re-run
Parallel runners collide on shared scratch filesUnique names per test (<TEST>_<RUN>_purpose.md), and file edits instead of shell heredocs
Role-players leak stage directions ("Vague on numbers:")Tell the executive its reply is pasted into the chat as is. Keep leaks verbatim and note them.
The AI judge is strict on borderline wordingRead the evidence quote before acting on a FAIL. Fix behaviour an executive would notice first.
Simulation is not the appFinish with a live check in a real Claude Project

11. Rebuild checklist

  • Clone the source read-only, and record the version and licence
  • Write the value review and agree the scope, exclusions and adaptations
  • Read the small method files and delegate the large ones to a digest subagent
  • Check the platform limits in the official docs, then present D1–D5 and wait for answers
  • Write the instructions: standing rules, mode chooser, one section per mode with output headings
  • Check that every question in the instructions is a single question
  • Write NOTICE.md (source map and MIT notice), LICENSE and the attribution line
  • Write the scenarios (two per mode, hidden facts and a trap each) and the runner protocol
  • Pilot one test, fix the protocol and any cross-cutting failures
  • Run the remaining tests four at a time, labelled by version
  • Tabulate failure patterns, fix root causes, bump the version, add a changelog entry, re-test the failures
  • Write the README, quick-start and test report, reporting failures plainly
  • Live check in a real Claude Project before publishing
